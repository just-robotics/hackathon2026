Разбор robot_body_filter

Полный путь облака точек от подписки до публикации: какая функция что делает, что получает на вход, что отдаёт и почему устроена именно так. Статическая часть работает и проверена; в конце — план второго этапа: поворотные колёса и откидная крышка.

статика: работает динамика: план 3 единицы трансляции без PCL Eigen + tf2

Путь одного облака

Всё, что происходит с сообщением от callback до publish. Пунктирные стрелки — точки, которые уходят из облака; они никуда не копируются, просто не попадают в выходной буфер.

Один проход по буферу. Промежуточных облаков между боксами нет.

Стадия за стадией

Нумерация здесь — реальный порядок вызовов за один кадр, а не оформление. Стадии 1–3 выполняются один раз при старте, 4–9 — на каждое облако.

Объявляет base_frame, publish_body_markers, tf_timeout, затем зовёт declareBoxes и отдаёт результат в filter_.setStaticBoxes(). Создаёт TF-буфер со слушателем, подписку на ~/input/pointcloud и два publisher'а.

Почему QoS разный. Облако — SensorDataQoS() на вход и выход (best effort, depth 5): согласовано с драйвером лидара, потеря кадра лучше задержки. Маркеры — QoS(1).transient_local(): RViz, подключившийся позже, сразу получает последнее сообщение.

RobotBodyFilterNode::declareBoxes(prefix, dynamic)

src/robot_body_filter_node.cpp

вход
prefix = "static_boxes" | "dynamic_boxes"; dynamic = читать ли axis и joint_frame
выход
std::vector<CropBox>, отбракованные боксы пропущены

Сначала читает <prefix>.names как string[], и только потом, зная имена, объявляет поля каждого бокса: origin, min, max, padding.

Почему список имён обязателен. declare_parameter требует точное имя параметра, а необъявленные параметры rclcpp отбрасывает при загрузке YAML — из конфига их не перечислить. Имена приходится объявить первыми, чтобы построить остальные ключи.

Валидация, после которой бокс пропускается с RCLCPP_ERROR:

ПроверкаПричина
origin/min/max ≠ 3 эл.неполные координаты дали бы тихо неверный бокс
padding ≠ 3 эл.раздутие задаётся вектором по осям, скаляр не принимается
min > maxперевёрнутый интервал не поймает ни одной точки
axis ≈ 0ось вращения нулевой длины не нормализуется
joint_frame пустдинамический бокс без звена нечем поворачивать

padding читается как double[3] и раздувает габариты по каждой оси отдельно, axis нормализуется на месте.

CropBox::updateTransform()

src/crop_box.cpp

вход
поля origin, min, max, padding, rotation
выход
axis_aligned, world_to_box, aabb_min, aabb_max

Вся предподготовка бокса. Вызывается из сеттеров фильтра и (в будущем) из applyJointPose. Развилка по rotation: 

axis_aligned = rotation.isApprox(Matrix3d::Identity(), 1e-9);

// ветка 1: бокс параллелен base_link
world_to_box = Isometry3d(Translation3d(-origin));
aabb_min = origin + padded_min;
aabb_max = origin + padded_max;

// ветка 2: повёрнутый бокс
world_to_box = box_to_world.inverse();
// AABB строится по 8 повёрнутым углам
for (int i = 0; i < 8; ++i) { ... cwiseMin / cwiseMax ... }
Зачем AABB у повёрнутого бокса. Он заведомо больше самого бокса, поэтому как точный тест не годится — но как предфильтр отсекает почти всё облако шестью сравнениями, до всякой матрицы. Биты i&1, i&2, i&4 перебирают комбинации min/max по трём осям — это и есть 8 углов.
Почему это не в конструкторе. CropBox — агрегат с публичными полями, его собирают присваиванием. Единая точка пересчёта нужна и после смены угла джоинта, а не только при создании.

RobotBodyFilter::updateGlobalAabb()

src/robot_body_filter.cpp

вход
static_boxes_, dynamic_boxes_ с готовыми aabb
выход
global_aabb_min_, global_aabb_max_, has_boxes_

Объединяет AABB всех боксов покоординатным cwiseMin / cwiseMax. Вызывается из обоих сеттеров.

Почему считается, а не задаётся числом. Куб «3 на 3 метра» из конфига разошёлся бы с боксами при первой же правке, и точки в вынесенном боксе перестали бы вырезаться молча. Здесь покрытие гарантировано по построению.

RobotBodyFilterNode::cloudCallback(msg)

src/robot_body_filter_node.cpp

вход
PointCloud2::ConstSharedPtr в кадре сенсора
выход
публикация в ~/output/pointcloud

Точка входа на каждый кадр. Проверяет is_dense, переводит облако в base_frame, зовёт filter(), публикует результат и пишет статистику в RCLCPP_DEBUG.

Проверка is_dense вместо isfinite на точку. Раньше в горячем цикле стояли три std::isfinite на каждую точку. Теперь — один разовый флаг с варнингом раз в 2 секунды. NaN-точки проходят насквозь: все сравнения с NaN дают false, поэтому в бокс такая точка не попадёт и просто уедет в выход.

RobotBodyFilterNode::transformCloudToBaseFrame(in, out)

src/robot_body_filter_node.cpp

вход
облако в произвольном кадре
выход
true + облако в base_frame; false — кадр пропускается

Если frame_id уже равен base_frame — копия без работы. Иначе lookupTransform на timestamp облака с таймаутом tf_timeout и tf2::doTransform.

Почему облако к боксам, а не боксы к облаку. Боксы заданы в base_link и их пять; кадр сенсора один. Перевести облако один раз дешевле, чем пересчитывать пять боксов в кадр сенсора на каждом кадре — и не пришлось бы трогать world_to_box каждого.

При отсутствии TF — RCLCPP_WARN_THROTTLE раз в 2 секунды и return false: кадр пропускается целиком. Отфильтровать наполовину хуже, чем не отфильтровать.

RobotBodyFilter::filter(cloud_in, cloud_out)

src/robot_body_filter.cpp — горячий путь

вход
облако в base_frame
выход
FilterStats; cloud_out без точек робота

Единственное место, где время действительно тратится. Схема повторяет faster_filter из autoware_pointcloud_preprocessor. 

// смещения полей — один раз на облако, не на точку
x_offset = fieldOffset(cloud_in, "x");

// одна аллокация на худший случай
cloud_out.data.resize(cloud_in.data.size());

for (offset = 0; offset + point_step <= data.size(); offset += point_step) {
    memcpy(&x, &data[offset + x_offset], sizeof(float));

    near_robot = has_boxes_ && /* 6 сравнений с global AABB */;
    if (near_robot && isPointInsideAnyBox(point)) { ++removed; continue; }

    memcpy(&out[output_size], &data[offset], point_step);
    output_size += point_step;
}

cloud_out.data.resize(output_size);  // усечение, без перевыделения
Три решения, которые держат производительность. Один resize вперёд вместо push_back — ни одной реаллокации в цикле. Копирование точки одним memcpy на весь point_step — intensity, ring, timestamp едут целиком, и код ничего не знает про XYZIRC. Предфильтр по глобальному AABB — точка в 20 метрах от робота уходит по шести сравнениям без единого умножения.

Ранний выход: если полей x/y/z нет или облако пустое, на выход идёт копия входа. Поля header, fields, point_step, is_dense переносятся со входа; height = 1, width и row_step пересчитываются.

is_dense пробрасывается, а не выставляется в true. NaN-точки больше не удаляются, поэтому обещать плотность нельзя — иначе облако уехало бы дальше по пайплайну с ложным флагом.

CropBox::contains(point) · insideAabb(point)

src/crop_box.cpp · crop_box.hpp (inline)

вход
точка в base_frame
выход
лежит ли она внутри бокса с учётом padding

Три ступени, каждая отсекает раньше следующей:

if (!insideAabb(point)) return false;   // 6 сравнений, 0 умножений
if (axis_aligned)       return true;    // AABB и есть сам бокс

const Vector3d local = world_to_box * point;   // 9 умножений
return (local.array() >= (min - padding).array()).all()
    && (local.array() <= (max + padding).array()).all();
Почему точка идёт к боксу, а не наоборот. У повёрнутого бокса нет дешёвого теста в координатах base_link — понадобились бы 6 плоскостей, это 18 умножений на точку. Перевод точки в локальную СК бокса даёт 9: строки world_to_box — те же нормали граней, но противоположные грани переиспользуют одну нормаль с двумя порогами.
Для текущего конфига третья ступень не исполняется. Корпус и мачта параллельны base_link, axis_aligned = true, и матрица не применяется ни разу за всё время работы.

Цена одной точки

Порядок ступеней выбран так, чтобы дорогое считалось для как можно меньшего числа точек. Доли — для типичного скана, где робот занимает малую часть поля зрения.

глобальный AABB6 сравнений · 0 умножений
Проходят все точки. Подавляющее большинство здесь же и заканчивает путь — и сразу копируется в выход.
AABB бокса · insideAabb6 сравнений × число боксов
Только точки в габаритах робота. Перебор с ранним выходом на первом попадании.
world_to_box · point9 умножений · 9 сложений
Только повёрнутые боксы и только точки внутри их AABB. При axis_aligned не выполняется вообще.
Что сюда сознательно не попало: кватернион вместо матрицы (15–18 умножений на вектор против 9 — он выигрывает на композиции поворотов, которых здесь нет), ограничивающая сфера вместо AABB (3 умножения против нуля, и отсекает слабее), pcl::CropBox (потребовал бы конвертации PointCloud2 ↔ PCL, а это дороже всей арифметики фильтрации).

План: динамическая часть

Второй этап. Покрывает поворотные колёса и откидную крышку — для кода это один и тот же случай: звено с одной степенью свободы, чья поза приходит из TF.

Решение, на котором держится остальное

Параметр axis убирается, поза берётся из TF целиком. Изначально задумывалось выделять скалярный угол вокруг заданной оси. Для поворотного колеса это неверно: в TF приходит композиция рулевого поворота и качения, и проекция такой композиции на одну ось даёт бессмысленное число.

joint_frame указывает на стойку, а не на колесо. Качение не меняет геометрию колеса — оно тело вращения вокруг своей оси. Поза стойки содержит только рулевой поворот, то есть ровно то вращение, которое двигает бокс. Поза колеса содержала бы ещё и качение, и бокс крутился бы на ходу без физической причины.

Следствие для конфига: origin и ориентация приходят из TF, в YAML остаются только габариты относительно СК звена.

Конфиг после изменений

dynamic_boxes:
  names: [wheel_front_left, wheel_front_right, lid]

  wheel_front_left:
    joint_frame: steer_front_left_link   # стойка, не колесо
    min: [-0.28, -0.09, -0.28]           # относительно СК стойки
    max: [ 0.28,  0.09,  0.28]
    padding: [0.03, 0.03, 0.03]

  lid:
    joint_frame: lid_link
    min: [-0.60, -0.40, -0.02]
    max: [ 0.60,  0.40,  0.02]
    padding: [0.03, 0.03, 0.03]
    angle_range: [0.0, 1.4]              # рад, необязательно
шаг 1CropBox: убрать axis, добавить swept-AABB
  • Убрать поле axis и его чтение из конфига.
  • Добавить swept_aabb_min / swept_aabb_max — куб, покрывающий бокс при любом допустимом угле. Считается один раз при загрузке.
  • Добавить angle_range (необязательное). Задан — swept строится как объединение AABB бокса в N положениях внутри диапазона. Не задан — радиус описанной сферы от origin, то есть полный оборот.
  • applyJointPose(): origin = pose.translation(), rotation = pose.linear(), затем updateTransform().
шаг 2RobotBodyFilter: swept в глобальный AABB
  • updateGlobalAabb() берёт у статических боксов обычный aabb, у динамических — swept_aabb. Снимается нынешний TODO.
  • updateDynamicBoxes() больше не зовёт updateGlobalAabb(): swept от текущего угла не зависит, пересчитывать нечего. Это убирает работу с горячего пути.
шаг 3Нода: чтение и разрешение поз
  • declareBoxes(dynamic=true): убрать axis и origin, добавить необязательный angle_range.
  • Вернуть lookupJointPoses(stamp, poses) — lookupTransform по каждому joint_frame в порядке jointFrames().
  • В cloudCallback перед фильтрацией: разрешить позы, при неудаче — warn и return, кадр пропускается целиком.
шаг 4Проверка
  • TF стойки с ненулевым рулевым углом: точки внутри и снаружи повёрнутого бокса.
  • Два разных угла руля — вырезаются разные точки.
  • Отсутствующий TF — облако не публикуется.
  • Крышка с angle_range: swept покрывает оба крайних положения.
Зачем angle_range понадобился именно из-за крышки. У колеса шкворень проходит близко к центру бокса, описанная сфера компактна. У крышки петля с краю и плечо длинное: крышка 1.2 м даёт swept-куб 2.4 × 2.4 × 2.4 вокруг петли, хотя реально она живёт в четверти этого объёма. На корректность это не влияет — swept только предфильтр — но раздувает глобальный AABB, и больше точек доходит до перебора боксов.
Открытый вопрос вне динамики: скошенность скана. Сейчас одна поза на всё облако. У вращающегося лидара точки размазаны по времени оборота, и на ходу колёса уезжают из маски. Лечится интерполяцией позы по полю времени точки — но это меняет сигнатуру разрешения поз.
Проверить перед реализацией: есть ли в дереве TF отдельные фреймы стоек. Если есть — план применим как есть. Если в дереве только base_link → wheel_link с обоими вращениями сразу, понадобится выделять рулевой угол из позы колеса, и это отдельный шаг.
