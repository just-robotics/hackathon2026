# Текущий контур после удаления MPC (01.10.2026)

MPPI — единственный исполнитель: основной официальный Nav2 C++1.1.20,
предыдущая Python-адаптация выбирается явно. MPC, его подмодуль и fallback
удалены из рабочего дерева по запросу пользователя. Исторические сравнения
ниже относятся к прежним версиям и не являются действующими командами запуска.

Native выполняет ±0,5м/с, PathAngle без forward preference, PreferForward выключен.
GoalAngle динамически включается только guardian/CAPTURE. Это параметры
штатных critics; исходная библиотека не переписывалась. Обёртка продолжает
проверять весь перемещаемый footprint. final cmd_vel выдаёт hsl_motion_gate,
который закрывает движение при неактуальных данных или отсутствии checked
MPPI command; скрытого геометрического/другого controller fallback нет.
Проверка synthetic free map подтверждает обе команды и изменение heading mode,
но движение в Gazebo нового варианта ещё не подтверждено серией.

# Адаптация локального MPPI из Nav2 Humble

**Текущий статус (01.10): прямой MPPI — основной исполнитель.**
В режиме `HSL_CONTROL_MODE=mppi` оптимизатор публикует первое управление в
`navigation/mppi_cmd_vel`; единственный финальный издатель `cmd_vel` — шлюз,
который проверяет разрешение, свежесть и безопасность. `local_path` показывает
ближайший префикс оптимизированной траектории. Для `OK` и `RECOVERY_MPPI`
шлюз использует MPPI, при проверенном fallback без прямой команды — MPC.
Исходный `mpc_motion_control` с его YAML сохранён; `HSL_CONTROL_MODE=mpc`
и длинные `global`/`smoothed` маршруты остаются запасным режимом.
Модель прямого MPPI согласована с периодом 0,2 с и штатным пределом 0,5 м/с;
Это период Python-адаптации; экспериментальный оригинальный C++ MPPI
установлен и работает с model_dt=0,05 с и частотой управления 20 Гц.

**История сравнения с передачей Path в MPC.**
Проба поставить перед ним пространственную дугу RPP откатана после дуэлей:
она отклонялась на большинстве циклов и не улучшила скорость.
Повторная сверка исходного кода показала принципиальную разницу интерфейсов:
`MPPIController::computeVelocityCommands` возвращает `TwistStamped`, а
`getOptimizedTrajectory()` вызывается для визуализации. Наша передача этой
временной траектории отдельному Lat-MPC не эквивалентна работе Nav2 MPPI.
Прямое следствие, наблюдаемое в трассах дуэлей: частые почти совпадающие точки
повышают оценку кривизны у Lat-MPC и понижают `v_curve`; прореживание точек
улучшило геометрическую метрику, но вызвало контакты со стеной. Пробная дуга
RPP тоже была адаптацией геометрии, а не полным Nav2 контроллером. Сравнение
серий приведено в [PROJECT_STATUS.md](PROJECT_STATUS.md).

Различия, важные для испытаний:

- Nav2 MPPI непосредственно выдаёт `cmd_vel`; в основном режиме адаптация
  также выдаёт команду через защитный шлюз. В резервном режиме оптимизированный
  `nav_msgs/Path` исполняет отдельный Lat-MPC, что требует самостоятельной проверки.
- Горизонт оптимизации и длина опубликованного пути различаются. Префикс
  ограничен по длине; это адаптация к контроллеру, требующая экспериментальной
  проверки длины пути и непрерывности между обновлениями.
- Штраф начальной касательной, возможность выбрать один безопасный образец
  вместо среднего, короткий повторный горизонт и recovery являются местными
  решениями. Их следует сохранять только при улучшении реальных заездов.
- В прямом режиме `max_speed` ограничен штатным `v_cmd_max=0,5`;
  модель учитывает измеренные скорости и ограничения ускорения. В резервном
  режиме intent до 1 м/с и штатное регулирование CC-MPC всё ещё различаются;
  результаты этих режимов следует сравнивать по фактическому движению.
- ROS `controller_server`, плагин C++ MPPI, Nav2 costmap и набор critics из
  исходного пакета здесь не запускаются. Поэтому полная эквивалентность Nav2
  не заявляется.

## Эксперимент с официальной библиотекой C++

Пакет `hsl_nav2_control` — оболочка над установленным `ros-humble-nav2-mppi-controller`, а не ещё один перенос формул. Официальные optimizer, noise generator, motion model и critics выполняются библиотекой. Оболочка предоставляет наблюдения, собственный Nav2 costmap, seed, путь A*, публикацию команд и короткую визуализацию оптимизированной траектории. Перед выпуском команды проверяется весь перемещаемый footprint с промежуточными отсчётами. Первый native кандидат добавлял tracking margin Python (.14/.12 м) в твёрдый контур; это создало расхождение с радиусом A* и проверяется отдельной корректировкой. Параметры кандидата находятся в `src/hsl_nav2_control/config/native_mppi.yaml`.

Исходный Python MPPI остаётся default; резервный MPC сохранён. Native проверен короткими дуэлями, но ещё не достиг критериев цели: серия
`series-20260930T234955Z` дала три поимки без контактов и ноль целей исследователя. Устанавливаемая версия apt наблюдалась как `1.1.20-1jammy.20260908.012051`; её нужно фиксировать в runtime перед сравнением. Совпадение установленной версии с ранее изученным commit исходников не предполагается.

При первом ROS запуске обнаружено требование official ObstaclesCritic: при consider_footprint=true costmap должен иметь явный footprint. Оболочка задаёт 32-угольник вокруг диска радиуса .37/.35 м, чтобы сохранить прежний запас, а не отключать проверку. Эта корректировка подтверждена запуском обоих стеков в серии `230724Z`; движение оказалось хуже Python, native не принят как default.

Проверка 1.1.20 выявила семантику GoalAngleCritic: конечный quaternion reference задаёт желаемую ориентацию. Native recovery теперь передаёт направление выхода, обычная навигация — касательную последнего сегмента; capture сохраняет ориентацию на соперника. Recovery-ссылка повторно проверяется по свежим наблюдениям перед публикацией. Гипотеза исправления ещё требует серии. Первоисточник: https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_mppi_controller/src/critics/goal_angle_critic.cpp .

После диагностики native collision radius берётся из `costmap.robot_radius`, кандидат.23м совпадает с A* и содержит5.2см относительно collision cylinder.178м в Xacro.32-угольник описан вокруг этого диска. Дополнительное предпочтение держаться дальше от препятствий остаётся в штатном ObstaclesCritic, а не добавляется повторно в размер корпуса. Полный swept-check сохранён. Успех этого кандидата пока не доказан.


## Повторная сверка версии 1.1.20 (01.10)

У [PathAngleCritic этой версии](https://github.com/ros-navigation/navigation2/blob/1.1.20/nav2_mppi_controller/src/critics/path_angle_critic.cpp)
параметр выбора направления называется `forward_preference` (bool), а не
`mode`. Поле `mode: 0` текущего кандидата не влияет на библиотеку; действует
значение по умолчанию `forward_preference=true`. При `vx_min=0` библиотека
принудительно сохраняет предпочтение вперёд. Для отдельной проверки
разрешённого заднего хода нужны отрицательный `vx_min` и явный
`forward_preference=false`; PreferForwardCritic может сохранять мягкое
предпочтение обычной езды вперёд. Кандидат настроен на vx_min=-0,35 и forward_preference=false;
результат дуэли ещё не получен.

Полный swept-check остаётся обязательным для любого знака скорости.
Отрицательная скорость — возможность выхода из тесноты и немедленного
ухода от угрозы, а не критерий хорошей обычной навигации. Нужны сравнение
скорости, отклонения, ускорений, исходов и отсутствие контактов.


Серия `series-20261001T001350Z` с разрешённым reverse дала3 цели explorer
без контактов, но0 поимок; guardian seed16 следовал назад512/622 активных
pose-отсчётов и имел среднюю скорость0,134м/с. Следующий launch-кандидат
задаёт официальный `MPPI.PathAngleCritic.forward_preference=true` guardian
и false explorer: направлению корпуса стража соответствует условие поимки.
Диапазон скоростей обоих сохранён −0,35…0,5м/с; результат этой роли-настройки
ещё требует фактической дуэли.


## Текущий запуск и проверка critic reverse (01.10)

Основной auto выбирает официальный C++ MPPI; предыдущие утверждения выше
о Python default относятся к историческим кандидатам. Роли теперь имеют
PathAngle.forward_preference=true у guardian и false у explorer. Это
проверено сериями encounter и scenario1 с обоими исходами, но scenario3
по-прежнему выявляет слабую навигацию explorer (результаты в статусе).
Оба автономных planner/gate требуют общий свежий `/match/active` referee:
частичное разрешение первого робота не даёт ему раннего движения.

Новый отдельный опыт da7f83f отключает стандартный PreferForwardCritic
только у explorer. В исходнике1.1.20 он штрафует интеграл отрицательной vx;
при weight5 это может противодействовать уже разрешённому reverse. У guardian
critic остаётся включён. Это настройка официальной библиотеки, а не изменение
optimizer/модели или снятие collision-check. Остальные critics и пределы
−0,35..0,5м/с /1,5рад/с сохранены. Runner проверяет реальные значения обоих
направляющих critics по роли. Улучшение скорости/исходов этого опыта пока
не доказано; последующий агент должен прочитать новые результаты в статусе.

Первый сопоставимый seed18 после отключения PreferForward explorer:
скорость0,224 против0,131м/с, RMS global0,067 против0,069м, без контактов
и recovery; angular accel RMS вырос0,563→0,792рад/с². Это одиночный опыт
с поимкой и без цели explorer, требуется повторение и другие старты.

Следующий опыт отключает GoalAngleCritic только у explorer: его площадка
и промежуточная точка отхода не задают ориентацию корпуса. При reverse
касательная reference может быть противоположна корпусу; штатный critic
требовал доворот возле такой точки. Guardian сохраняет GoalAngle для поимки.
Это настройка требований к цели; эффект требует реального сравнения на
втором физическом старте с теми же условиями.

01.10 следующий изолированный кандидат: стандартный PathAngleCritic weight
2→6 у обоих роботов, без изменения скоростей/остальных critics/footprint.
Медленное начальное выравнивание подтверждено трассами; польза усиления
ещё не доказана, результаты и критерии отката — в PROJECT_STATUS.
