# Цель проекта и состояние модулей

Этот документ связывает задачи разработки с [регламентом HSL26](<Регламент HSL26 - v06092026.pdf>). Ссылки на страницы ниже относятся к PDF версии от 06.09.2026. При расхождении формулировок приоритет у регламента и разъяснений организаторов. Текущее состояние проверок ведётся в [PROJECT_STATUS.md](PROJECT_STATUS.md), команды запуска — в [README.md](../README.md).

## Цель

Подготовить автономное ПО для предоставляемого организаторами TurtleBot 2 с Livox Mid-360, способное провести матч в обеих ролях:

- **Исследователь (explorer):** добраться до стартовой площадки стража и избежать поимки. Достижение площадки фиксируется при касании её контура контуром робота.
- **Страж (guardian):** обнаружить и догнать исследователя. Поимка фиксируется только при одновременном выполнении трёх условий: расстояние между системами координат роботов меньше 0,45 м; ось X стража отклонена от направления на исследователя не более чем на 45°; между роботами нет препятствия.

Если исследователь не пойман к завершению этапа, этап засчитывается в его пользу. Количественная система баллов в регламенте не опубликована: её обещано сообщить в первый день. Матч выигрывает команда с большим числом баллов за оба этапа (раздел 5.3, с. 5–6).

## Условия, влияющие на ПО и испытания

| Условие регламента | Следствие для разработки |
| --- | --- |
| Полигон — лабиринт из модулей примерно 1 × 1 м. Его конфигурацию объявят в первый день и не изменят во время соревнований. Статические препятствия расставлены заранее неизвестным, но одинаковым для команд образом; их ширина и длина от 0,1 м, высота от 0,15 м, поверхности непрозрачные и не зеркальные (раздел 5.1, с. 4). | Решение должно работать с неизвестной заранее расстановкой препятствий. Сведения, ставшие известными в первый день, нужно отличать от заранее неизвестных особенностей испытаний. |
| Матч состоит из двух симметричных этапов по 10 минут; команды поочерёдно играют исследователя и стража. В начале каждого этапа даются 4 минуты подготовки: робот не должен пересекать ограничительную линию стартовой площадки. После этого он может начать движение независимо от соперника (разделы 5.2–5.3, с. 5). | Нужны обе роли и управляемый переход от подготовки к движению. Время этапа и запрет раннего выезда нужно учитывать в сценариях проверки. |
| Подготовка робота проводится только с ПК организаторов и через SSH. Исходный код разрешено редактировать лишь во время подготовки, до пересечения стартовой линии и после согласования с организатором (раздел 5.2, с. 5). | Запуск должен быть воспроизводимым без ручной настройки на другом компьютере во время заезда. |
| Во время соревнований нельзя фиксировать в ПО прямо или косвенно сведения о заранее неизвестных особенностях испытаний. Запрещены дополнительная сенсорика, сетевое оборудование, средства увеличения производительности бортового ПК, изменение конструкции и внешнего вида робота (раздел 5.2, с. 5). | Планировать решение в рамках штатного робота и Livox Mid-360; не закладывать в код скрытую конфигурацию препятствий. |
| За столкновения со статическими препятствиями штрафов нет. Судьям рекомендована информативная индикация в терминал. Возможны один полный перезапуск этапа по совместному запросу капитанов или решению организаторов, остановка капитаном и перезапуск при критическом смещении элементов полигона (разделы 5.2–5.3, с. 5–6). | Диагностика роли, состояния и ключевых событий в терминале полезна для судейства; алгоритм и запуск должны переживать повторный старт этапа. |

Это рабочие следствия для проекта, а не дополнительные правила соревнования. Организационные и спорные вопросы решают организаторы (разделы 3 и 5.3).

## Что сейчас есть в репозитории

Инвентаризация обновлена по текущей ветке 02.10.2026. Фактические проверки и ограничения перечислены в [PROJECT_STATUS.md](PROJECT_STATUS.md).

| Компонент | Наличие и фактическая функция |
| --- | --- |
| `src/sim_kobuki/` | Модель Kobuki и мир `polygon_rosbag.world` для Gazebo Classic. Одиночный launch из `main` сохранён; отдельный `launch_duel.launch.py` создаёт двух роботов с раздельными темами и TF. |
| `src/jr_map/`, `src/jr_launch/` | `/map` — аналитическая `OccupancyGrid` из известного SDF-мира, а не SLAM. `jr_launch` запускает карту и инструменты сенсорного стенда. |
| `src/hsl_interfaces/`, `src/hsl_decision/` | `PlanningIntent` и выбор поведения для исследователя и стража с явным разрешением движения и задержкой переключения. |
| `src/hsl_planning/` | Накопленные 3D-точки, текущий скан и при наличии симуляционная сетка проецируются на проходимость. A* строит глобальный путь. Основной локальный контур — официальный C++ плагин Nav2 Humble MPPI в собственной оболочке `hsl_nav2_control`, выдающий команду скорости и короткий Path для визуализации, с полной проверкой перемещаемого контура. Предыдущая Python-адаптация MPPI и MPC удалены по запросу пользователя; границы интеграции описаны в [NAV2_MPPI_ADAPTATION.md](NAV2_MPPI_ADAPTATION.md). |
| `src/hsl_nav2_control/` | Оболочка официального `nav2_mppi_controller`, отдельные costmap и наблюдения каждого робота, прямые команды MPPI через защитный шлюз. Это единственный локальный контроллер; это не запуск `controller_server`. |
| `src/hsl_perception/` | Python/NumPy-детектор формы корпуса и Kalman-трекер из `feature/detector`. Входы: собственные scan/self и статическая known_grid; текущие simulation/real профили различаются. Ложные треки коробок остаются открытой проблемой. |
| `src/hsl_sim_adapter/`, `src/hsl_debug_control/` | По одному адаптеру собственной точной симуляционной локализации, облаков и метрик на робота. Referee и метрики используют ground truth для судейства. MPPI выдаёт команды через отдельные защитные шлюзы. Сценарный патруль и отладочный контроллер пути удалены. |
| `helm_launch/`, `docker/` | CLI `helm`, Compose и образ на базе Autoware / ROS 2 Humble с Gazebo Classic 11, Livox SDK/драйвером и ROS-пакетами. |
| Профили `gazebo`, `simulation`, `duel` | Один робот; сенсорный стенд с картой; отдельный двухроботный навигационный контур соответственно. |
| `vehicle`, `sensing`, `localization`, `perception`, `api`, `transforms`, `debug` | Контейнеры-заготовки без автономных узлов. Профиль `simulation` содержит сенсорный стенд с картой и инструментами; автономный запуск — `duel`. |

В `duel` эта цепочка повторяется для обоих роботов: Gazebo → адаптер и LiDAR-детектор → decision manager → глобальный путь → штатный Nav2 MPPI → защитный шлюз → команда скорости → Gazebo. Шлюзы удерживают нулевую команду до явного разрешения движения и при устаревших данных. По плану команды статическая карта реального лабиринта будет снята заранее в разрешённый период подготовки; картографирование во время заезда не планируется. Текущий `/map` получен непосредственно из файла симуляционного мира и нужен для отладки. Два автономных стека уже многократно проверялись друг против друга в Gazebo; устойчивость, плавность и минимальная средняя скорость пока не подтверждены. Реальный стек собирается отдельно с драйверами из `drivers/src`.
Статическая карта `maze_bag_v1` и AMCL дают map→odom и `/navigation/self`.
Собственные LiDAR-возвраты фильтруются до AMCL/навигации. На оборудовании
есть заезды, но текущие исправления блокировки движения ещё не подтверждены.
Текущий пользовательский критерий цели — центр площадки с допуском 0,08 м;
это строже регламентного касания. Текущие профили времени: simulation 360 с,
real 600 с активного времени; для регламентной оценки явно задавайте 360 с.

## Открытые части автономного контура

Открыто: устойчивость real-локализации и движения при собственных LiDAR-возвратах,
ложные треки коробок, очистка динамических отметок после перемещения/удаления
препятствий, recovery, точность финиша при толкании коробок и повторная оценочная
серия текущей версии. Карта, AMCL и детектор уже подключены; их физическую
устойчивость ещё нужно подтвердить. Стартовые позы задавайте по фактическому
полигону. Переносимость на другой лабиринт экспериментально не доказана.
