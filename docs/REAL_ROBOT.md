# Реальный Kobuki + Livox Mid-360

## Что запускается

Отдельный Compose-проект `hsl-real`, контейнер `real`, образ
`jr_real_image:latest`, на базе организационного образа HSL25
`nickodema/kobuki:humble-22.04-100625` (digest закреплён в Dockerfile).
Он взят из добавленного комплекта `hsl25-master (1)/hsl25-master/kobuki/docker`.
Симуляция продолжает использовать свой `jr_image`; real не зависит от него.
Для работы контейнера NVIDIA не требуется.

```text
Kobuki USB → /odom → map-поза → decision → global planner → Nav2 MPPI → gate → /cmd_vel → Kobuki
Livox Ethernet → /livox/lidar → cloud в map → planner / MPPI / detector
```

Все узлы работают по системному времени (`use_sim_time=false`). Gazebo,
симуляционный источник позы, второй робот и судья с ground truth здесь не
запускаются. Используются текущие алгоритмы и параметры скорости; отдельного
«ограничения скорости для реального этапа» нет. В предоставленном исправлении
kobuki_core действуют собственные пределы драйвера:0.4м/с и3рад/с,
ускорение/торможение0.3/0.7м/с² и3.5/5.2рад/с². Они применяются после
команды MPPI или ручного шлюза; команда0.5м/с не означает такую же скорость
базы. Ограничитель включён в обоих real режимах.

Локализация — официальный Nav2 AMCL: высотный срез Livox сопоставляется
со статической картой. Kobuki публикует `/odom` и `odom → base_footprint`;
AMCL публикует `/amcl_pose` (PoseWithCovarianceStamped, frame map) и
**динамический** `map → odom`. Статической привязки в режиме amcl нет.
URDF публикует `base_footprint → base_link`, mounting — `base_link → livox`.
`real_observations` переводит одометрию через поправку AMCL в
`/navigation/self` (Odometry, frame map): именно её получают decision,
планировщик и MPPI; LiDAR также переводится в map на timestamp облака.
Таким образом, `/amcl_pose` — оценка фильтра, `/navigation/self` — текущая
поза между обновлениями фильтра, распространённая по свежей одометрии.

## 1. Подготовка компьютера

Выполните обычную установку Docker и helm из [README](../README.md).
Команды ниже выполнять из корня репозитория на компьютере робота.

Один раз установите правило USB:

```bash
sudo install -m 644 drivers/udev/30-kobuki.rules /etc/udev/rules.d/30-kobuki.rules
sudo udevadm control --reload-rules
sudo udevadm trigger --subsystem-match=tty
ls -l /dev/kobuki
```

При необходимости переподключите USB базы. Если устройство называется иначе,
укажите реальный путь, например `/dev/ttyUSB0`, в `config/real.yaml`.

Подключите Livox к Ethernet. В перенесённом комплекте настройки такие:

- LiDAR: `192.168.88.105`;
- компьютер: `192.168.88.205`;
- UDP-порты: 56100–56501, как в `config/livox_mid360.json`.

Проверьте свой интерфейс (`ip -br address`). Пример назначения адреса —
замените `enp3s0` именем своего Ethernet-интерфейса:

```bash
sudo ip link set enp3s0 up
sudo ip address add 192.168.88.205/24 dev enp3s0
ping -c 3 192.168.88.105
```

Если адрес уже назначен, повторно добавлять его не нужно. При другом адресе
компьютера замените все host IP в `config/livox_mid360.json`; адрес самого
LiDAR задаётся в `lidar_configs[].ip`. Host networking контейнера сохраняет
эти адреса и UDP-порты без перенаправления.

## 2. Настройки до запуска

`config/real.yaml`:

| Поле | Смысл |
| --- | --- |
| mission_file | Реальная миссия, по умолчанию `real_match.yaml` |
| kobuki_port | USB-порт базы |
| livox_config | JSON сетевых настроек LiDAR |
| lidar_mount | `[x,y,z,roll,pitch,yaw]` от base_link до livox; метры/радианы |
| localization | `amcl` по умолчанию; `odometry` без коррекции или `external_tf` |
| localization_file | `localization.yaml`, параметры AMCL/среза/готовности |
| odom_topic / lidar_topic | Входные топики драйверов |
| map_file | `maps/maze_bag_v1.yaml`, статическая карта Nav2 |
| arena_bounds | Границы допустимого движения в map, `[xmin,ymin,xmax,ymax]` |
| ros_domain_id | По умолчанию 26, отдельно от симуляции |
| rviz | Показывать RViz; по умолчанию false |

Mounting `[0,0,0.3,0,π,π/2]` перенесён из HSL25. Проверьте его соответствие
фактической установке LiDAR: неверные высота/поворот исказят препятствия.

В `config/real_match.yaml` задайте реальные `robot.role`, `robot.start`,
`opponent.start`, размеры площадок, motion и match. Координаты — в map.
`robot.start` должен соответствовать фактическому положению базы в момент
нового запуска драйвера. Секция `simulation` при реальном запуске не задаёт
мир или карту; здесь используются `arena_bounds` из `real.yaml`.
Исследователь стремится к центру `opponent.start`, допуск 0,08 м.
`allow_reverse` действует только на исследователя; страж всегда едет передом.

Файлы должны лежать внутри каталога конфигурации. Для отдельного комплекта
настроек скопируйте весь `config/` и установите путь:

```bash
export HSL_REAL_CONFIG=/absolute/path/to/robot-config/real.yaml
```

Этот путь действует для всех команд ниже. Можно иметь отдельный mission YAML,
чтобы изменения реальной миссии не меняли настройки симуляции.
На одном ROS_DOMAIN_ID должен работать один такой робот: запуск пока без
namespace. Для второго независимого робота назначьте другой domain.

## 3. Сборка и пересборка

Первая сборка и после изменений кода, launch, URDF или Dockerfile:

```bash
helm stop_real       # если робот сейчас запущен
helm build_real
helm start_real
```

`build_real` собирает только реальный образ: пять пакетов `drivers/src` в
`/workspace/install`, затем наше решение из `src/hsl_*` в `/solution/install`.
Livox SDK2 уже есть в организационном образе. Gazebo, Autoware и SLAM в
реальный образ не добавляются. Docker использует cache. Для замены базового
образа можно задать `REAL_BASE_IMAGE`, для имени результата — `REAL_IMAGE`.
Образ сам по себе не меняет уже работающий контейнер: после сборки используйте
`start_real`, который пересоздаёт только контейнер `hsl-real`.

После правки только YAML/JSON из `config/` достаточно `stop_real` и
`start_real`: пересборка не нужна. Конфигурация примонтирована read-only и
читается при новом запуске. Новый запуск обнуляет одометрию/таймер этапа;
сначала верните базу в указанную стартовую позу либо исправьте `robot.start`.

## 4. Запуск

```bash
helm start_real      # драйверы + весь стек, движение запрещено
helm status_real     # состояние контейнера
helm logs_real       # логи; Ctrl+C завершает только просмотр
```

`start_real` проверяет наличие USB-порта. Если драйвер или основной узел
завершается, launch останавливает весь стек. При включении `rviz` передайте
DISPLAY и доступ к X11 своего компьютера; DISPLAY и X11 socket передаются
Compose. В терминале графической сессии можно разрешить локальный доступ
контейнерному root командой `xhost +si:localuser:root`. Закрытие RViz не
завершает стек. Используется отдельный `hsl_real/config/robot.rviz` с одним
роботом, scan и путями; Map display выключен до появления карты, его можно
включить в панели Displays.

Посмотрите данные, открыв отдельный терминал:

```bash
helm enter_real
ros2 topic hz /odom
ros2 topic hz /livox/lidar
ros2 topic echo /navigation/native_ready --once
ros2 run tf2_ros tf2_echo map base_footprint
ros2 run tf2_ros tf2_echo base_link livox
ros2 topic info /cmd_vel --verbose
```

Из контейнерного терминала выход — `exit`. Наличие `/odom` и сырого LiDAR ещё
не означает готовность: должны поступать `/navigation/self` и
`/navigation/scan` в map с корректными TF и свежими timestamps.

Для начала движения:

```bash
helm enable_real
```

Команда ждёт готовности MPPI, свежих pose/scan, незавершённого этапа и проверяет
единственного publisher `/cmd_vel` (`hsl_motion_gate`). Затем выдаёт разрешение.
Kobuki подписан на этот же `/cmd_vel` через remap `commands/velocity`.
Сценарного патруля и teleop в этом запуске нет.

## 5. Пауза и остановка

```bash
helm pause_real      # запретить движение, оставить драйверы и навигацию
helm enable_real     # продолжить незавершённый этап
helm stop_real       # запретить движение, затем остановить контейнер и драйверы
```

На паузе таймер активного времени не идёт. Через `match.active_seconds`
активного движения или при достижении центра исследователем этап закрывается.
После этого нужен новый `start_real`, возобновление не разрешается.
Для стража нет симуляционного судьи: регламентную поимку в реальном мире
определяет внешний судья/оператор; завершение вручную — `pause_real`/`stop_real`.

При пропаже свежих данных gate отправляет нулевую команду. При прекращении
команд сам драйвер Kobuki применяет свой timeout 0,6 с. Команды остановки
работают и при некорректно отредактированном YAML.

## 6. Карта и локализация

`config/real.yaml` уже использует `maps/maze_bag_v1.yaml` и `localization: amcl`.
Карта выровнена по основным стенам на +1,8°, XY-ноль — внутренний левый нижний угол основных стен;
+X вправо, +Y вверх, yaw0 вправо. Начало записи примерно[0.15,0.15]; [координаты и ограничения карты](../config/maps/README.md).
`robot.start` задаёт **начальное приближение AMCL**, а не фиксирует дальнейшую
позу. Шаблон соответствует месту/ориентации начала записи. `opponent.start`
в поставляемой миссии — пример, его нужно заменить реальной площадкой.
Монтаж LiDAR и точный сдвиг относительно базы пока не откалиброваны.

`localization.yaml` задаёт срез0,10–0,40м над base_footprint, дальность0,25–8м,
угловые ячейки0,5°. Официальный pointcloud_to_laserscan сначала преобразует
облако в base_footprint, затем берёт ближайшую точку каждого направления.
AMCL likelihood_field использует 500–2000 частиц, колёсную одометрию и скан.
Здесь нет SLAM, обновления стен или FAST-LIO в аппаратном запуске.
Источники: [Nav2 AMCL](https://api.nav2.org/nav2-humble/html/amcl__node_8cpp_source.html),
[pointcloud_to_laserscan](https://github.com/ros-perception/pointcloud_to_laserscan).

Сначала пересоберите образ, затем запустите без разрешения движения:

```bash
helm build_real
helm start_real
helm enter_real
ros2 topic echo /localization/status
ros2 topic echo /amcl_pose --once
```

`/localization/status` показывает актуальность скана/odom/позы/TF и
неопределённость. `/localization/ready` публикуется10Гц. Разрешение требует
свежих данных и стандартного отклонения позиции≤0,20м (большая ось XY-эллипса),
угла≤0,35рад. Пороги настраиваются в YAML. Во время стоянки monitor просит
`/request_nomotion_update` каждые0,5с, чтобы AMCL обновлялся без движения.
Ковариация — оценка фильтра, она не доказывает правильность совпадения в
симметричном лабиринте. До enable проверьте наложение скана на стены.

Для RViz установите `rviz: true` и пересоздайте start_real. Карта включена,
**2D Pose Estimate** отправляет `/initialpose`: укажите положение базы и
направление её переда на карте. После уточнения дождитесь ready=true и
в другом терминале выполните `helm enable_real`. При потере готовности
`/match/active=false`, permission отзывается; восстановление локализации
само не возобновляет движение, требуется новый enable_real.

Для другой карты меняются map_file, arena_bounds и стартовые позы.
Режим odometry оставлен для проверки драйверов; он не исправляет дрейф.
external_tf ожидает сторонний map→odom. Не публикуйте второй map→odom
при работающем AMCL. Ручной bag-режим AMCL не запускает и карту не требует
для обработки сенсорных топиков (но конфигурация должна быть валидной).

## Проверка без подключённой базы

Сборка/ROS-интерфейсы проверяются на тестовых odom/cloud без доступа к USB.
Это не подтверждает физическую езду, точность одометрии, монтаж LiDAR,
пропускную способность реального потока или отсутствие столкновений на базе.
Фактический hardware smoke test после подключения робота остаётся обязательным
этапом проверки; до него выполнение реальной навигации не заявляется.

## 7. Запись bag с клавиатурой

Откройте обычный интерактивный терминал на компьютере робота:

```bash
helm start_real_bag_record
```

Запускаются только Kobuki, Mid-360, TF/URDF, ручной шлюз и MCAP recorder.
Автономные decision/planner/MPPI не запускаются. Оба реальных режима используют
один контейнер: переход из одного режима в другой сначала штатно останавливает
предыдущий. Сценария картографирования нет.

Клавиши: `i` — вперёд, `,` — назад, `j`/`l` — поворот, `k` — стоп.
Диагональные `u`/`o`/`m`/`.` совмещают движение и поворот. Пределы скорости
берутся из `motion` миссии. Клавиатура публикует `/real/keyboard_cmd_vel`;
единственный издатель финального `/cmd_vel` — `real_manual_gate`.
Если вход прекращается, через `keyboard_timeout_s` (по умолчанию 0,6 с)
шлюз отправляет стоп. `pause_real`/`enable_real` также управляют ручным шлюзом.

**Ctrl+C закрывает клавиатуру, запись продолжает работать.** В этом или другом
терминале завершите сессию:

```bash
helm stop_real
```

Сначала закрывается движение, затем контейнер получает SIGINT. Recorder
закрывает MCAP и записывает `metadata.yaml`; `stop_real` проверяет его наличие.
При ошибке возвращается ненулевой код, файлы сохраняются для разбора.
Не используйте `docker kill` для завершения записи.

Данные на хосте:

```text
recordings/<UTC>-bag/
  bag/                 # *.mcap + metadata.yaml
  session.json         # версия Git, dirty flag, режим, итог сохранения
  real.yaml
  match.yaml           # либо имя mission_file
  recording.yaml
  livox_mid360.json     # либо имя livox_config
```

Каталог результатов можно заменить через `HSL_REAL_DATA_DIR=/absolute/path`.
Список топиков задаётся в `config/recording.yaml`: odom, LiDAR, IMU, TF,
joint_states, cmd_vel и сенсоры/диагностика. Настроенные odom/lidar автоматически
добавляются, если их имена отличаются. Отсутствующие топики recorder ждёт;
завершённый файл сам по себе не доказывает, что все датчики публиковали данные.

Для просмотра записи:

```bash
docker run --rm -v "$PWD/recordings:/records:ro" --entrypoint bash jr_real_image:latest -lc \
  'source /solution/install/setup.bash && ros2 bag info /records/<UTC>-bag/bag'
```

При изменении Python/C++/launch/драйверов выполните `stop_real`, `build_real`
и снова нужный старт. После изменений YAML/JSON нужна только перезапуск сессии.
Оригинальные bag-файлы из `HSL26-ros2_bags` не изменяются.

Офлайн-подготовка статической карты по записи описана в
[OFFLINE_MAPPING.md](OFFLINE_MAPPING.md). Для обработки сохраните всю сессию,
включая конфиги: геометрия mounting и стартовая привязка нужны вместе с bag.

## Диагностика автономного заезда

Каждый `helm start_real` создаёт `recordings/<UTC>-autonomous/`, сохраняет
миссию, hardware/localization конфиги и карту, пишет MCAP с исходным Livox,
odom/TF, AMCL, localization ready/status, собственным/чужим треком, intent,
глобальной/локальной траекторией, MPPI/planning диагностикой, match и cmd_vel.
После заезда используйте `helm stop_real`, чтобы завершить metadata.yaml.
В консоли печатается каталог сессии. При следующем старте старая сессия
сначала штатно останавливается. Это позволяет разбирать recovery/стены/финиш
по синхронным данным; прошлый автономный заезд без bag восстановить нельзя.

Площадки0.5×0.5м задаются start_area_half_size:0.25 для обеих сторон. Целью
исследователя остаётся центр с допуском0.08м. real_match проверяет каждую
свежую map-позу, завершает этап сразу при достижении центра и отзывает
permission; decision также запоминает достижение. Шум позы после финиша
не заставляет исследователя снова уехать из площадки. Размер площадки
не является размером корпуса или допуском goal center.
